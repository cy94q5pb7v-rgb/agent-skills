# drawio

Скилл превращает Claude в инженера-диаграммиста, который собирает редактируемые схемы в формате **draw.io** (он же **diagrams.net**) прямо из текстового описания — без визуального холста. Результат — файл `.drawio`, который пользователь открывает двойным кликом в десктопном приложении draw.io или загружает на app.diagrams.net, и там свободно двигает, перекрашивает и дополняет.

## Целевой формат

`.drawio` — это **XML-файл** (текстовый формат с тегами, как HTML). Внутри — дерево из узлов (`mxCell` с `vertex="1"`) и связей (`mxCell` с `edge="1"`). Файл полностью редактируемый: в отличие от картинки (PNG/SVG), пользователь может в draw.io подвинуть любой блок, поменять текст, добавить стрелку.

**Почему генерируем XML напрямую, а не картинку:** диаграмма должна оставаться живой. Пользователь почти всегда хочет потом что-то поправить сам. Картинку править нельзя, `.drawio` — можно.

**Один файл = одна диаграмма** (или несколько вкладок-`<diagram>` внутри одного `<mxfile>`, если страниц несколько).

## Когда применять

- Любая просьба про схему/диаграмму/блок-схему с явным или подразумеваемым требованием редактируемости.
- Прямое упоминание draw.io / diagrams.net / `.drawio`.
- Оргструктуры, бизнес-процессы, архитектура ПО, схемы БД (ER), сетевые диаграммы, mind map, user-flow, customer journey.

**Когда НЕ применять:** если нужна именно картинка для вставки в документ без правок — это может быть быстрее через SVG/HTML. Если нужна интерактивная веб-схема — это `/interactive-prototype` или HTML. Если речь про строгую нотацию BPMN с методологией — есть отдельный скилл по BPMN; этот делает «практичные» процессные схемы, а не методически выверенный BPMN 2.0.

## Принципы

**Не выдумывай данные.** Если пользователь дал список отделов, людей, шагов процесса — рисуй ровно их. Если данных не хватает (например, не названы роли в оргструктуре) — спроси, а не сочиняй. Пустой, но честный каркас лучше красивой выдумки.

**Раскладка по сетке — не «куча».** draw.io не делает авто-раскладку за тебя при генерации XML: координаты `x`/`y` каждого узла ты задаёшь руками. Поэтому держи в голове сетку. Узлы выравнивай по колонкам и рядам с равным шагом. Стрелки не должны пересекать узлы. Шаг сетки — 10px (`gridSize="10"`), координаты кратны 20–40.

**Связи осмысленные.** Каждая стрелка должна означать конкретное отношение (поток, подчинённость, зависимость, переход). Не соединяй всё со всем. Если связей слишком много и схема превращается в паутину — сгруппируй узлы в контейнеры (`swimlane`) или разбей на несколько страниц.

**Иерархия читается за 3 секунды.** Главное — крупнее/выше/левее (мы читаем сверху-вниз, слева-направо). Цветом выделяй смысловые группы, а не «чтобы было ярко».

**Борьба с «ИИ-эстетикой».** Не делай радужный винегрет, где каждый блок своего цвета. Палитра — 2–4 смысловых цвета максимум (см. ниже). Без аляповатых теней и градиентов. Текст в блоке — короткий: заголовок + 1 строка пояснения, не абзац.

## Рабочий процесс

### Фаза 0. Контекст (без вопросов, если данные есть)

Прочитай бриф. Если в нём уже есть **тип диаграммы** и **содержимое** (список узлов/шагов/отделов) — сразу к Фазе 2. Если пользователь приложил файл/код/таблицу как источник — прочитай и извлеки структуру оттуда.

### Фаза 1. Уточнение (только если реально не хватает)

Спрашивай **минимум** и только по делу:
- Какой **тип** диаграммы, если не очевидно (блок-схема / оргструктура / архитектура / ER / mind map / сеть / процесс).
- Само **содержимое**, если его нет (узлы и связи между ними).
- **Ориентация**: сверху-вниз или слева-направо (для процессов/деревьев).

Не задавай вопросов про цвета и шрифты, если пользователь сам не поднял тему — выбери разумные дефолты.

### Фаза 2. Раскладка на бумаге (в уме)

До генерации XML определи:
- Сколько узлов, как они группируются в ряды/колонки.
- Координатную сетку: ширина узла обычно `160–240`, высота `60–80`, горизонтальный шаг между колонками `+200…+280`, вертикальный между рядами `+120…+160`.
- Где контейнеры (`swimlane`), где простые узлы.
- Какие связи и куда входят/выходят.

### Фаза 3. Генерация .drawio

Возьми за основу подходящий шаблон из `templates/` и наполни своими узлами. Точная анатомия формата, все стили и приёмы — в `references/format.md`. **Прочитай этот файл перед первой генерацией**, если не уверен в синтаксисе.

Пиши файл в рабочую папку проекта (или туда, куда просил пользователь), имя — осмысленное: `<тема>.drawio`.

### Фаза 4. Открыть и проверить

Открой файл (см. «Как открыть» ниже). Затем **проверь себя**:
- Файл валиден (открылся без ошибки парсинга).
- Узлы не наезжают друг на друга, стрелки не проходят сквозь блоки.
- Все обещанные узлы и связи на месте, лишнего нет.
- Текст помещается в блоки (не обрезан).

Если открыть приложением нельзя (нет десктопного draw.io, headless-среда) — честно скажи пользователю: «файл готов, открой его в app.diagrams.net (File → Open) или в десктопном draw.io» и приложи путь.

## Анатомия .drawio (кратко)

Полная шпаргалка — в `references/format.md`. Минимальный скелет:

```xml
<mxfile host="app.diagrams.net" agent="Claude" version="22.1.0">
  <diagram id="diag1" name="Схема">
    <mxGraphModel dx="1400" dy="900" grid="1" gridSize="10" page="1" pageWidth="1600" pageHeight="1100" math="0" shadow="0">
      <root>
        <mxCell id="0"/>
        <mxCell id="1" parent="0"/>
        <!-- узел -->
        <mxCell id="n1" value="Старт" style="rounded=1;whiteSpace=wrap;html=1;fillColor=#dae8fc;strokeColor=#6c8ebf;" vertex="1" parent="1">
          <mxGeometry x="80" y="80" width="160" height="60" as="geometry"/>
        </mxCell>
        <mxCell id="n2" value="Готово" style="rounded=1;whiteSpace=wrap;html=1;fillColor=#d5e8d4;strokeColor=#82b366;" vertex="1" parent="1">
          <mxGeometry x="80" y="240" width="160" height="60" as="geometry"/>
        </mxCell>
        <!-- связь n1 -> n2 -->
        <mxCell id="e1" style="edgeStyle=orthogonalEdgeStyle;rounded=0;html=1;" edge="1" parent="1" source="n1" target="n2">
          <mxGeometry relative="1" as="geometry"/>
        </mxCell>
      </root>
    </mxGraphModel>
  </diagram>
</mxfile>
```

Ключевые правила:
- `id="0"` и `id="1"` — служебные корневые ячейки, **всегда** должны быть. Все узлы имеют `parent="1"` (или id контейнера).
- Узел = `vertex="1"` + `<mxGeometry x y width height>`. Связь = `edge="1"` + `source`/`target` (id узлов) + `<mxGeometry relative="1">`.
- Координаты узла внутри контейнера (`swimlane`) — **относительно контейнера**, не абсолютные.
- Спецсимволы в `value` экранируй: `&` → `&amp;`, `<` → `&lt;`, `>` → `&gt;`. Перенос строки — реальный `\n` внутри значения или `&#10;`.

## Плейбук по типам диаграмм

- **Блок-схема (flowchart):** старт/конец — скруглённые (`rounded=1`); действие — прямоугольник; решение — ромб (`rhombus`). Поток сверху-вниз, ветвления решения подписывай на стрелках («Да»/«Нет»). Шаблон: `templates/flowchart.drawio`.
- **Оргструктура:** дерево сверху-вниз, один корень, ортогональные связи (`edgeStyle=orthogonalEdgeStyle`). Уровни = ряды с равным `y`. Шаблон: `templates/orgchart.drawio`.
- **Архитектура ПО:** слои/группы в контейнерах `swimlane`, компоненты внутри, стрелки = потоки данных/вызовы. Подписывай протоколы на стрелках при необходимости. Шаблон: `templates/architecture.drawio`.
- **ER / схема БД:** сущности — таблицы (`shape=table` или простой прямоугольник с разделами), связи — линии с кардинальностью (1, *, 1..*). См. `references/format.md`.
- **Mind map:** центральный узел, радиальные ветви, скруглённые узлы, без стрелок (просто линии).
- **Сетевая диаграмма:** иконки-узлы (можно `shape=mxgraph.*` из библиотеки), связи = каналы.

## Палитра (дефолт draw.io)

Используй стандартные «мягкие» пары fill/stroke draw.io — они аккуратны и узнаваемы:

| Назначение | fillColor | strokeColor |
|---|---|---|
| Нейтральный / процесс | `#dae8fc` | `#6c8ebf` (синий) |
| Успех / выход | `#d5e8d4` | `#82b366` (зелёный) |
| Внимание / решение | `#ffe6cc` | `#d79b00` (оранжевый) |
| Ошибка / стоп | `#f8cecc` | `#b85450` (красный) |
| Группа / контейнер | `#f5f5f5` | `#666666` (серый) |
| Акцент | `#e1d5e7` | `#9673a6` (фиолетовый) |

2–4 цвета на схему. Один цвет = один смысл.

## Как открыть .drawio

Скилл кроссплатформенный. Открой файл одним из способов:

- **Windows (десктоп draw.io):** `cmd //c start "" "C:\путь\file.drawio"` — откроется в установленном приложении draw.io. Если не установлено: `winget install JGraph.Draw`.
- **macOS:** `open file.drawio` (если установлено приложение draw.io) или `open -a "draw.io" file.drawio`.
- **Linux:** `xdg-open file.drawio` или AppImage draw.io.
- **Веб (всегда работает, без установки):** скажи пользователю открыть https://app.diagrams.net → **File → Open from → Device** → выбрать файл. Содержимое не покидает браузер (diagrams.net не загружает файл на сервер).

В headless/CI-среде приложение не открывай — просто сообщи путь и предложи app.diagrams.net.

## Антипаттерны

- ❌ Радужная палитра — каждый блок своего цвета. Максимум 2–4 смысловых цвета.
- ❌ Узлы, наезжающие друг на друга, и стрелки сквозь блоки. Считай координаты.
- ❌ Длинные абзацы внутри блока. Блок = заголовок + максимум 1 короткая строка.
- ❌ Выдуманные данные (имена, отделы, цифры), которых не было в брифе.
- ❌ Эмодзи как иконки, если пользователь не просил. (В legacy-схемах автора они встречаются — не копируй привычку.)
- ❌ Связи «всё со всем» — если получается паутина, группируй в контейнеры или дроби на страницы.
- ❌ Незакрытый/невалидный XML, отсутствие служебных `id="0"`/`id="1"`, неэкранированные `&`/`<`/`>` в тексте.
- ❌ Тени и градиенты ради «красоты» (`shadow="0"` в модели, не включай).

## Чеклист перед сдачей

1. XML валиден, файл открывается без ошибки парсинга.
2. Есть служебные `mxCell id="0"` и `id="1"`.
3. Все узлы из брифа на месте; ничего лишнего не добавлено.
4. Узлы не пересекаются, стрелки не проходят сквозь блоки, текст не обрезан.
5. Палитра ≤ 4 цветов, один цвет = один смысл.
6. Файл открыт в приложении/предложено открыть в app.diagrams.net, путь указан пользователю.
