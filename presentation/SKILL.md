# presentation

Скилл превращает агента в дизайнера-аналитика презентаций, который собирает **один автономный HTML-файл** со слайдами 1920×1080 — открывается двойным кликом в любом браузере, листается стрелками `← →` / пробелом, печатается в PDF. Движок встроен в файл, внешняя зависимость одна — веб-шрифт (есть системный фолбэк).

Две опоры скилла:
1. **Аналитика, а не пересказ.** Скилл читает исходный материал, вытаскивает факты и числа, **считает производные** (доли, динамику, суммы) — но только из реальных данных — и показывает цифры там, где они сильнее текста.
2. **Аккуратная вёрстка без догадок.** Слайды строятся из готовых сеток, которые не переполняются и **заполняют кадр**, а в конце дека проверяется скриптом-аудитором.

## ⚡ ЯДРО — 5 пунктов (если удержишь только это, уже выйдет нормально)

1. **Спроси и жди.** Фаза 1: режим + вводные простым текстом → дождись ответа, не начинай без него.
2. **План в файл.** `presentation/<тема>.plan.md`: блоки + **Реестр данных** (числа с источником) + план на **РОВНО N слайдов**, по которым распределена ВСЯ информация.
3. **Числа — только из реестра.** Ничего не выдумывай; нет данных — не показывай.
4. **Каждый слайд — форма из содержания**, формы варьируй; стиль уже Сбер (`:root` не трогай); заполняй кадр.
5. **Прогони `audit.mjs`** (`--selftest`, затем аудит `--plan`): `FAIL` → чини; нет браузера → сверь высоту вручную. Без аудита не сдавай.

Всё остальное ниже — детализация этих пяти пунктов.

## Что на входе и выходе

- **Вход:** тема + вводные (Фаза 1). Сильно желателен **источник** — документ/текст/таблица/цифры, на которых строится дека.
- **Куда сохранять:** все файлы — в папку **`presentation/`** в рабочей директории. Нет такой папки — **создай её** перед записью (`mkdir presentation`; на Windows `New-Item -ItemType Directory -Force presentation`).
- **Выход (результат):** **один файл** `presentation/<тема>.html` — самодостаточный, движок встроен, оффлайн-готовый (кроме веб-шрифта). Никаких отдельных `.js` рядом.
- **Рабочий файл:** `presentation/<тема>.plan.md` — внешняя память скилла (реестр данных, план слайдов, дизайн-решения), нужна при сборке. Это **единственный** служебный файл; в конце предложи удалить его или оставить как бриф. Больше ничего не плоди.
- **Язык:** по входным данным; по умолчанию русский. Шрифт обязан поддерживать язык (кириллица — `references/layout-system.md` §7).

## Когда применять / когда нет

Применяй на любую просьбу про презентацию/слайды/deck/питч, открывающиеся в браузере.

**Не применяй**, если нужен редактируемый PowerPoint как главный артефакт, или это интерактивный веб-прототип, а не линейные слайды.

## Принципы (читать до начала)

- **⛔ СНАЧАЛА СПРОСИ — ПОТОМ ДЕЛАЙ.** ВСЕГДА начинай с вопросов (Фаза 1): режим работы + ключевые вводные. Задай их **простым нумерованным списком прямо в чат** (или интерактивным инструментом выбора, если он есть в CLI — `AskUserQuestion`/`ask`), затем **ОСТАНОВИСЬ и дождись ответа** — не анализируй и не верстай, пока пользователь не ответил. НЕ полагайся на наличие специального инструмента: нет его — спрашивай обычным сообщением и жди. **Единственное исключение** — пользователь сам явно написал «не спрашивай / сделай сам». «Мне и так всё понятно из брифа» — НЕ повод пропустить: всё равно задай вопросы (слабая модель плохо судит, достаточно ли данных, — поэтому всегда спрашивай).
- **Форма следует за содержанием.** Нет «шаблона на каждый слайд», в который пихается текст. Для КАЖДОГО слайда сам определи идеальную форму из того, что он должен сказать: число → крупная цифра/график; противопоставление → сравнение; процесс → шаги; перечень аспектов → колонки; одна мысль → тезис; доказательство → цитата/факт. Роли-раскладки (`layout-system.md`) — это **словарь готовых непротекаемых блоков**, которые ты адаптируешь и комбинируешь под контент, а НЕ меню, под которое подгоняешь информацию. Шаблон `deck.html` — это **СКЕЛЕТ** (движок + стили), готовых слайдов в нём НЕТ: проектируй каждый слайд заново под содержание, **ВАРЬИРУЙ формы** (не повторяй одну подряд), и **первый слайд — тоже по содержанию**, а не автоматически обложка.
- **Сначала структура, потом вёрстка.** Раздроби материал на блоки → построй план всей деки (что на каком слайде) → спроектируй форму каждого слайда → собери. Не начинай верстать, пока нет плана.
- **Внешняя память — пиши в файл, не держи в голове.** Модель под gigacode слабая и «забывает», когда контекст растёт. Поэтому весь анализ, **реестр данных**, план слайдов и дизайн-решения сразу пиши в рабочий файл `<тема>.plan.md` и **перечитывай его** перед сборкой каждого слайда — не полагайся на память. Бонус: процесс возобновляемый (контекст слетел → продолжил с файла). Шаблон файла и механика — `references/pipeline.md`.
- **Дроби работу на узкие шаги / субагентов.** Тяжёлые куски (анализ большого источника, сборка каждого слайда, фикс по аудиту) делай отдельными сфокусированными задачами с чистым контекстом — чтобы не забивать общий контекст и не путать слабую модель. Поддерживает CLI субагентов/`Task` — делегируй (субагент-сборщик получает только план-файл + спеку одного слайда + словарь форм и возвращает один `<section>`); не поддерживает — иди последовательно, перечитывая план-файл. Рецепты — `references/pipeline.md`.
- **Ничего не выдумывай.** Цифры, факты, цитаты, названия — только из брифа/источника или посчитанные из них. **Нет данных в исходнике — НЕ показывай** (не дописывай «правдоподобные» числа и общие фразы). Лучше убрать блок/слайд, чем выдумать. Пустой, но честный — допустимо; выдуманный — нет.
- **Анализируй и считай.** Не пересказывай текст буллетами. Извлеки числа, посчитай **производные из реальных данных** (доли %, рост/динамику, суммы, средние, «было → стало») и покажи их (роль `stats` / `chart`), если это сильнее текста.
- **Заполняй кадр.** Свободного пространства должно быть мало: контент занимает ~85–95% полезной области, а не «висит» в центре с пустыми полями. Пустует низ/бока → увеличь типографику и блоки, добавь реальный элемент (цифру, мини-график, инсайт) или объедини слайды. Пустота = недоделанность (см. `layout-system.md` §2). **Исключение — тезис / цитата / обложка** (`statement`/`quote`/`cover`): им по природе положен воздух, правило 85–95% к ним не применяется (аудит их за недозаполнение и не штрафует).
- **Ровно столько слайдов, сколько просил пользователь — и вмести в них ВСЁ.** Распредели всю информацию по заданному числу слайдов: приоритизируй, объединяй, уплотняй (на один слайд может лечь несколько связанных блоков). **НЕ создавай лишние слайды и НЕ обрезай контент.** Не помещается даже после уплотнения → **СПРОСИ** (увеличить число слайдов или что убрать). Молча терять/резать информацию — нельзя. Не задано число — выбери уместное под объём материала.
- **Возник вопрос — спроси.** Данные неоднозначны, непонятна структура слайда, не хватает факта для расчёта, не ясна аудитория/акцент → задай вопрос пользователю (инструментом выбора, если он есть; иначе — простым текстом) и **жди ответа**. Не угадывай и не выдумывай в обход вопроса.
- **Один слайд — одна мысль.** Не влезает — дели.
- **Заголовок — это вывод, а не тема** (action title). По одним заголовкам читается вся история (ghost-deck test).
- **Борьба с «ИИ-эстетикой»** обязательна (`references/anti-ai-checklist.md`).
- **Сначала проверь, потом сдавай** (`references/self-check.md`).

## Рабочий процесс

### Фаза 0. Контекст (без вопросов, если данные есть)

Прочитай бриф и **весь приложенный материал** (документ/текст/таблица/цифры). Если упомянут бренд/палитра/референс — учти. Не переспрашивай то, что уже дано.

### Фаза 1. Вопросы пользователю — ОБЯЗАТЕЛЬНЫЙ первый шаг (стоп-ворота ⛔)

**Всегда начинай с этого шага — задай вопросы и дождись ответа.** Единственное исключение: пользователь сам явно написал «сделай сам / не спрашивай». Во всех остальных случаях спрашивай, даже если кажется, что в брифе «и так всё есть» — НЕ решай за пользователя, что вопросы не нужны.

**Как задавать (не зависит от CLI):** есть интерактивный инструмент выбора (`AskUserQuestion` и т.п.) — используй его; **нет — напиши вопросы простым нумерованным списком в чат, заверши сообщение и жди ответа.** После вопросов **твой ход заканчивается — НЕ переходи к Фазе 2**, пока пользователь не ответил.

**1.0 — Режим работы (спрашивай всегда — это выбор пользователя):**
- **Авто** — соберу всю деку сам, покажу результат.
- **Послайдово** — по каждому слайду предложу 2–3 варианта + рекомендацию и дождусь выбора.

**1.1 — Вводные.** Уже явно данное в брифе не переспрашивай; спроси недостающее (консолидируй, не засыпай по одному):
1. **Тема и одна цель** — какое **одно** действие/решение нужно от зрителя.
2. **Тип деки** — **питч / отчёт-аналитика / статус / обучение / обзор** (предложи вероятный из цели и материала — пользователю остаётся подтвердить или сменить). Тип задаёт сквозную нить (архетипы — `pipeline.md` §1); не угадывай молча — это ключевой выбор.
3. **Аудитория** — кто смотрит, уровень, настрой.
4. **Объём** — слайдов или длительность (≈1–2 мин/слайд).
5. **Нужны ли цифры/метрики** — да, это ядро / по ситуации / нет, только смыслы.
6. **Источник данных для цифр** — в приложенном материале / пришлю отдельно / только из текста / данных нет.
7. **Плотность** — low (под доклад) / high (под чтение).
8. **Тон/бренд** — есть ли бренд-цвета/шрифты (для «Сбер» — пресет из `layout-system.md` §6).
9. **Заметки докладчика** — нужны ли.

**1.2 —** Чего-то не хватает по ходу работы — снова **спроси** (и жди ответа), не выдумывай дефолт по важному: данные, аудитория, акцент.

### Фаза 2. Анализ и архитектура → в файл `presentation/<тема>.plan.md`

Не верстай, пока не выстроена структура. **Результат этой фазы пишется в план-файл** (шаблон и подробности — `references/pipeline.md`). Большой источник анализируй **субагентом** (если CLI умеет), чтобы не тащить весь текст в общий контекст; иначе — сам.

1. **Создай папку `presentation/`** (если её нет) и в ней файл **`<тема>.plan.md`** по шаблону из `pipeline.md`.
2. **Раздроби материал на блоки** → секция «Блоки»: атомарные факты, идеи, числа, разделы, выводы (что главное / второстепенное / данные).
3. **Заполни «Реестр данных»** — таблица `Показатель | Значение | Источник (откуда/цитата) | Слайд`. Сюда **только реальные и посчитанные** значения; производные (доли %, динамика, суммы, «было → стало») считай из реального и тоже вноси с пометкой расчёта. **Нет данных — не вноси** (спроси или не показывай). Этот реестр = и память, и защита от выдумки: слайды берут числа ТОЛЬКО отсюда.
4. **По подтверждённому в интервью ТИПУ деки построй сквозную нить** (архетипы в `pipeline.md` §1; не навязывай pitch-структуру «проблема→решение» отчёту). **Построй «План слайдов» на РОВНО столько слайдов, сколько просил пользователь** (число задано → строго оно; не задано → выбери под объём). **Распредели по этим слайдам ВСЮ информацию** из блоков/реестра — уплотняй, объединяй связанные блоки на один слайд, приоритизируй; **не плоди лишние слайды и не обрезай**. Если всё не помещается даже после уплотнения — **спроси** (увеличить число или что убрать). Для КАЖДОГО слайда: сообщение (action-title) · что показать по сути (число/сравнение/шаги/перечень/цитата/тезис) · ссылки на строки реестра · приоритет (P0/P1/P2) · шаг нити. Форму НЕ фиксируй под шаблон — она выводится из «что показать» в Фазе 3. Прогони ghost-deck test.
5. **Дизайн-система** (секция файла): **по умолчанию — фирменный стиль Сбера (белый + зелёный + Golos), он уже зашит в шаблон.** Не меняй цвета и НЕ вводи новые — другой бренд только если пользователь его явно назвал. **При другом бренде** поменяй НЕ только токены `:root` (пресет/палитра — `layout-system.md` §6), но и **слово «Сбер» в рамке `.fr`** (→ имя бренда) и **точку-логотип** `.wm .dot` (→ сплошной цвет бренда), иначе чужая дека останется со словом «Сбер» и зелёной точкой. Реши также, где 1–2 инверсных слайда для ритма.
6. **Открытые вопросы** — выпиши и **задай пользователю** до вёрстки.

### Фаза 3. Сборка по плану — форма каждого слайда ИЗ содержания

Собирай **по одному слайду, каждый раз сверяясь с `<тема>.plan.md`** (не по памяти). Делегируй сборку слайда субагенту, если CLI умеет (он получает план-файл + спеку одного слайда + `layout-system.md`, возвращает один `<section>`); иначе строй сам, перечитывая план перед каждым слайдом.

**Путь сборки выбирается АВТОМАТИЧЕСКИ по простому правилу — не решай это сам:**
- CLI **не умеет** субагентов → собирай **сам, последовательно**, перечитывая план перед каждым слайдом; без агентства.
- CLI **умеет** субагентов → **субагент-сборщик на каждый слайд** + **независимый критик-арт-директор** (`anti-ai-checklist.md`) на ключевые (P0) слайды + QA через `audit.mjs`.

Полное «агентство» из 4 ролей и усилители (few-shot / голосование / финальный ревью) — **только по явной просьбе** пользователя или для важной внешней деки. Рецепты — `references/pipeline.md` §2 (субагенты/фолбэк) и §5 (роли и критик-циклы).

1. Скопируй `templates/deck.html` как **`presentation/<тема>.html`** (папку `presentation/` создай, если нет). **Стиль уже Сбер — `:root` НЕ трогай**, кроме явно названного другого бренда. Внутри `<deck-stage>` готовых слайдов НЕТ (это скелет) — собирай их заново по плану, **не «заполняй образец»**.
2. Для КАЖДОГО слайда из плана **выведи форму из «что показать»** (принцип «форма следует за содержанием»). `layout-system.md` §4 — **словарь непротекаемых блоков**: бери подходящий как основу, **адаптируй/комбинируй** под контент. Числа — строго из «Реестра данных», ничего сверх.
3. Дисциплина вёрстки: **заполняй кадр** (~85–95%), бюджет высоты, `data-fit`. **ВАРЬИРУЙ формы** — соседние слайды не должны быть одной структуры; **первый слайд проектируй по содержанию** (не автоматически обложка) и не делай его пустым титульником. Держи **ровно N слайдов** из плана, со всей информацией.

**Режим АВТО:** собери все слайды по плану (по одному, сверяясь с файлом) → Фаза 4 → покажи результат.

**Режим ПОСЛАЙДОВО:**
1. Сначала покажи пользователю **«План слайдов»** из файла и получи ОК — согласование структуры.
2. По каждому слайду предложи **2–3 варианта формы/наполнения, выведенных из содержания** + **свою рекомендацию**, с опцией «свой вариант» (инструментом выбора, если есть; иначе текстом — и жди ответа). Свёрстай выбранное, отметь слайд готовым в плане.
3. 1 компактный вопрос на слайд, не утомляй.
4. В конце — самопроверка (Фаза 4).

### Фаза 4. Самопроверка (обязательно, блокирует сдачу)

По **`references/self-check.md`**:
1. **Бюджет высоты + заполнение** — каждый слайд: ничего не вылезает И нет больших пустот.
2. **Аудитор.** Сначала `node scripts/audit.mjs --selftest` (есть ли браузер). Затем `node scripts/audit.mjs presentation/<тема>.html --plan presentation/<тема>.plan.md`. Он проверяет: переполнение/наезжание, **недозаполнение** слайда, **наличие рамки `.fr` и `.pg`**, **повтор форм подряд**, плейсхолдеры и **сверяет числа деки с «Реестром данных»** (числа не из реестра → WARN «проверь, не выдумано ли»). Любой `FAIL` → чини (можно фикс-субагентом, см. `pipeline.md`) и перезапускай; `WARN` → разберись. **Если в выводе «⚠️ ГЕОМЕТРИЯ НЕ ПРОВЕРЕНА» (браузера нет)** — проверена только структура; ОБЯЗАТЕЛЬНО сверь высоту слайдов вручную по бюджету (~590px под контент) и честно скажи пользователю.
3. **Нарратив** — action titles + ghost-deck test.
4. **Данные** — каждая цифра в деке **есть в «Реестре данных» плана**; ничего не выдумано. Если в HTML появилось число, которого нет в реестре — убери или найди источник.
5. Есть скриншоты/vision — пройди ручной визуальный чеклист.

### Фаза 5. Открыть и предложить дальнейшее

Открой файл (ниже) или дай путь. Предложи: **PDF** (Ctrl/Cmd+P → «Сохранить как PDF»), **PPTX** по-картинкам (если есть инструмент), заметки докладчика. **Спроси про `<тема>.plan.md`:** удалить (был рабочей памятью) или оставить как бриф/для правок и пересборки.

## Как открыть .html

- **Windows:** `cmd //c start "" "C:\путь\presentation\<тема>.html"`
- **macOS:** `open presentation/<тема>.html` · **Linux:** `xdg-open presentation/<тема>.html`
- В headless/CI не открывай — сообщи путь.

## Антипаттерны — жёстко нельзя

- ❌ Начать делать деку, не задав вопросы (когда пользователь не сказал «сделай сам»). Сначала спроси и **дождись ответа**; нет инструмента вопросов — спрашивай простым текстом, не пропускай шаг.
- ❌ Подгонять контент под готовый шаблон. Форму слайда проектируй ИЗ содержания; роли — словарь блоков, не меню.
- ❌ Верстать до плана. Сначала дробление на блоки и план всей деки, потом вёрстка.
- ❌ Выдуманные/«правдоподобные» цифры и факты. Нет в источнике — не показывай.
- ❌ Большие пустоты / «воздух» без причины. Заполняй кадр.
- ❌ Угадывать вместо вопроса, когда данные неоднозначны.
- ❌ Первый слайд всегда одной структуры (обложка `.layout-cover` по умолчанию) или пустой титульник. Проектируй и его под содержание.
- ❌ «Спасибо за внимание» на финале — вместо этого вывод + действие + контакт.
- ❌ Вводить новые/чужие цвета (красный, терракота, синий, фиолетовый). Используй ТОЛЬКО токены `:root` — по умолчанию фирменный Сбер (белый/зелёный). Менять палитру можно лишь под явно названный другой бренд.
- ❌ Тонкая линия-акцент под заголовком; эмодзи-иконки; фиолетовые градиенты; glassmorphism; дефолтные Inter/Roboto/Arial.
- ❌ Шрифт без поддержки языка (кириллица «квадратами»).
- ❌ Однотипные слайды по одному образцу (заполнять шаблон вместо проектирования). Варьируй формы под содержание.
- ❌ Раскидать информацию на больше слайдов, чем просил пользователь, и обрезать лишнее. Держи заданное N, вмещай всё уплотнением/объединением — или спрашивай.
- ❌ Сдать деку без `audit.mjs` (или, если браузера нет, не сказав об этом).
- ❌ Держать анализ и план «в голове» вместо `<тема>.plan.md` — слабая модель забудет и начнёт выдумывать.
- ❌ Плодить **черновики/копии**. Файлов всего два: результат `.html` + обязательный служебный `.plan.md`. (Это НЕ запрет на план-файл — его создавать нужно; нельзя плодить лишнее сверх этих двух.)

## Чеклист перед сдачей

1. Режим согласован; материал раздроблён на блоки, построен план деки, форма каждого слайда выведена из содержания; открытые вопросы заданы и закрыты.
2. Каждая цифра прослеживается в источнике/расчёте — ничего не выдумано.
3. `audit.mjs` без `FAIL` (или честно сказано, что браузер недоступен).
4. **Кадр заполнен** — нет больших пустот; контент на ~85–95% площади.
5. Заголовки — выводы; ghost-deck test проходит.
6. Раскладки чередуются; 1–2 инверсных слайда; палитра 60/30/10; шрифт поддерживает язык.
7. Пройден анти-ИИ чеклист; финал = вывод + действие.
8. Файл открыт / путь передан; предложены PDF/PPTX.
