# Оркестрация для слабой модели: план-файл + субагенты

gigacode под капотом — **слабая модель** (Qwen/DeepSeek). Её слабые места: «забывает» данные и решения, когда контекст растёт; плохо тянет один большой проход (вся дека за раз); склонна выдумывать. Лечим тремя приёмами:

1. **Внешняя память** — весь анализ/план/данные живут в файле `<тема>.plan.md`, а не «в голове». Перед сборкой каждого слайда модель перечитывает оттуда нужное.
2. **Маленькие сфокусированные задачи** — анализ, сборка каждого слайда, фиксы — по отдельности, с чистым контекстом (субагентами, если CLI умеет; иначе последовательно).
3. **Реестр данных с источниками** — числа берутся только из таблицы, где у каждого указан источник. Нельзя взять то, чего нет → нельзя выдумать.

---

## 1. План-файл `<тема>.plan.md` (внешняя память)

Создаётся в Фазе 2 рядом с будущей декой. Это единственный служебный файл. Шаблон:

```markdown
# План презентации: <тема>

## Бриф
- Тема / Цель (одно действие) / Аудитория:
- Режим: авто | послайдово   ·   Язык:   ·   Плотность: low | high
- Бренд-пресет:   ·   Нужны ли цифры: да | по ситуации | нет   ·   Источник данных:

## Блоки (раздробленный материал — только то, что реально есть в источнике)
- Б1: <атомарный факт/идея>  — [источник: где взято]
- Б2: ...

## Реестр данных   (ТОЛЬКО реальные и посчитанные значения; слайды берут числа ТОЛЬКО отсюда)
| ID | Показатель | Значение | Источник / расчёт | Слайд |
|----|-----------|----------|-------------------|-------|
| D1 | выручка 2024 | 1,2 млрд ₽ | «отчёт, стр. 4» | S4 |
| D2 | рост г/г | +18% | расчёт: (1,2−1,02)/1,02 | S4 |
> Нет данных для показателя — НЕ вноси строку (спроси пользователя или не показывай число).

## Дизайн-система
- Палитра 60/30/10: фон … · акцент … · нейтраль …
- Шрифты (display / body / mono, с поддержкой языка):
- Инверсные (тёмные) слайды: №…   ·   Пресет: …

## План слайдов
### S1
- Сообщение (action-title): <вывод одной фразой>
- Что показать по сути: обложка | тезис | число | сравнение | шаги | перечень | цитата | график | визуал
- Данные: D… (ID из реестра) | нет
- Приоритет: P0 | P1 | P2   ·   Арка: завязка | проблема | решение | доказательство | вывод
- Статус: [ ] не собран
### S2
...
```

**Правила файла:** заголовки слайдов сразу как выводы (ghost-deck test — прочитал все `Сообщение` подряд → история читается). «Что показать» определяет ФОРМУ в Фазе 3 — конкретную раскладку заранее не фиксируй. Статус `[x]` ставится по мере сборки → процесс возобновляемый.

## 2. Сборка С субагентами (если CLI поддерживает Task/субагентов)

Орк (главный агент) держит тонкий контекст и раздаёт узкие задачи. Результаты субагентов он только вставляет в файлы.

### 2.1. Субагент-аналитик (один раз, если источник большой)
Зачем: не тащить весь текст источника в общий контекст.
> Промпт: «Ты аналитик. Прочитай источник: <путь/текст>. (1) Раздроби на атомарные блоки. (2) Извлеки ВСЕ числа и ключевые факты с указанием, откуда (цитата/раздел). (3) Посчитай уместные производные (доли %, динамику, суммы, «было→стало») ТОЛЬКО из реальных значений. Ничего не выдумывай — если данных нет, так и напиши. Верни строго две секции: «Блоки» (список) и «Реестр данных» (таблица ID|Показатель|Значение|Источник/расчёт). Без вёрстки и воды.»

Орк вставляет ответ в `## Блоки` и `## Реестр данных` плана, затем сам строит `## План слайдов` и `## Дизайн-система`.

### 2.2. Субагент-сборщик слайда (на КАЖДЫЙ слайд)
Зачем: маленькая граница задачи = слабая модель не путается и не переполняет.
> Промпт: «Собери РОВНО ОДИН `<section>…</section>` для слайда S{N}. Дано: (а) план-файл `<тема>.plan.md` — возьми из него спеку S{N} и нужные строки Реестра данных; (б) `layout-system.md` — словарь форм, фирменная рамка `.fr`, бюджет высоты, правило заполнения кадра, `data-fit`; (в) дизайн-токены из плана. Требования: форму выведи из поля «Что показать» (форма следует за содержанием) — бери блок словаря и адаптируй/комбинируй, не подгоняй контент под случайную роль. Числа — ТОЛЬКО из Реестра (по ID), больше никаких. Заполни кадр (~85–95%), не переполняй (поля 132/118, полезная область 1680×830), крупный текст помечай `data-fit`, включи блок рамки `.fr` с пустым `<span class="pg"></span>`. Верни ТОЛЬКО HTML секции, без пояснений.»

Орк вставляет полученный `<section>` в `<deck-stage>` строго по порядку S1…SN и ставит `[x]` в плане. Нумерацию слайдов движок проставит сам.

### 2.3. Субагент-фиксер (на упавший по аудиту слайд)
> Промпт: «`audit.mjs` сообщил по слайду S{N}: <reason>. Вот текущий `<section>` и `layout-system.md` (рычаги починки). Почини именно это (переполнение → меньше высота/шрифт, дели; наезжание → проверь absolute; плейсхолдер → реальный текст из реестра; пустота → крупнее/добавь реальный элемент). Верни исправленный `<section>` целиком.»

## 3. Сборка БЕЗ субагентов (фолбэк — CLI не умеет Task)

Тот же конвейер, но шаги делает сам главный агент, опираясь на файл вместо памяти:
1. Напиши `<тема>.plan.md` целиком (Фаза 2).
2. Скопируй `templates/deck.html` → `<тема>.html`, проставь токены из «Дизайн-системы».
3. **Цикл по слайдам:** перед каждым слайдом **перечитай** из плана его спеку + нужные строки Реестра (не по памяти!) → собери `<section>` → вставь в деку → поставь `[x]` в плане. Повторяй, пока все `[x]`.
4. Прогони `audit.mjs`; на каждый FAIL — перечитай слайд + рычаги, почини, перезапусти.

Контекст растёт → не страшно: источник истины в файле, всегда можно перечитать и продолжить.

---

## 4. Возобновляемость и очистка

- **Возобновление:** если контекст потерян/сессия прервалась — открой `<тема>.plan.md`, найди слайды без `[x]` и достраивай только их. Ничего не теряется.
- **Очистка (Фаза 5):** спроси пользователя — удалить `<тема>.plan.md` (был рабочей памятью) или оставить как бриф для будущих правок/пересборки. По умолчанию предлагай оставить, если дека делалась из сложного источника (пригодится), и удалить — если бриф был тривиальный.

## 5. Команда ролей (агентство) и циклы критики

Субагентов из §2 можно собрать в маленькое «агентство» с РАЗДЕЛЕНИЕМ ролей **мейкер ↔ критик**. Для слабой модели важнее не «больше исполнителей», а **независимый критик с конкретным чеклистом**: он ловит то, чего не видит тот, кто верстал. Десять слабых «синьоров» не дают синьорский результат — а связка «сделал → независимо раскритиковал → переделал» даёт.

| Роль | Что делает | Чем вооружён | Тип |
|---|---|---|---|
| **Контент-стратег** (нарратив) | дробит материал, реестр данных, план слайдов, action-titles, ghost-deck test | источник, §1 | мейкер |
| **Арт-директор** (senior designer) | фиксирует дизайн-систему (токены/шрифты/пресет), определяет ФОРМУ слайда из содержания, **критикует** собранный слайд на вкус и заполнение | `layout-system.md`, `anti-ai-checklist.md` | мейкер + критик вкуса |
| **Верстальщик** (senior developer) | собирает `<section>` строго по спеке арт-директора и реестру | `layout-system.md`, план-файл | мейкер |
| **QA-критик** | `audit.mjs`, сверка цифр с реестром, структурные проверки; список дефектов, блокирует сдачу | `audit.mjs`, `self-check.md` | критик геометрии/данных |

Оркестратор (главный агент) держит план-файл и гоняет цикл. **Два независимых критика = две оптики:** арт-директор ловит вкус / ИИ-слоп / пустоты (текстовая проверка по чеклисту), QA — геометрию и данные (скрипт). Ни одна по отдельности недостаточна.

### Цикл на каждый слайд: сделал → раскритиковал → переделал
1. **Арт-директор** пишет спеку слайда (форма из содержания + что показать + ID данных из реестра + акцент).
2. **Верстальщик** собирает `<section>` (промпт §2.2).
3. **Арт-директор критикует** — ОТДЕЛЬНЫМ вызовом, не тот, кто верстал:
   > «Оцени слайд по `anti-ai-checklist.md` и правилам: форма соответствует содержанию? кадр заполнен (~85–95%, без больших пустот)? есть ИИ-слоп (линия под заголовком, эмодзи, фиолетовый градиент, generic-фразы)? контраст читаем? Верни вердикт OK или список конкретных правок.»
   Есть правки → верстальщик переделывает (1 круг, максимум 2).
4. **QA-критик**: `audit.mjs` + сверка цифр с реестром. FAIL → фиксер (§2.3) → перезапуск аудита.

Слайд получает `[x]` только когда **оба** критика дали OK.

### Без субагентов
Тот же цикл, но одна модель **последовательно меняет шляпы**, а чеклисты-файлы играют роль «второго взгляда»: собрал слайд → ОТДЕЛЬНЫМ проходом, строго по `anti-ai-checklist.md`, придирчиво найди дефекты как арт-директор → исправь → `audit.mjs`. Разделение во времени + явный чеклист заменяют отдельного агента.

## 6. Масштаб под задачу (не пали ресурсы зря)

Агентство дорогое и медленное — включай по весу задачи:

- **Lite** (1–5 слайдов, простой бриф): стратег + верстальщик + `audit.mjs`. Без отдельного арт-критика — хватает чеклиста в один проход.
- **Standard** (по умолчанию): + арт-директор-критик на **P0-слайды** (обложка, ключевые выводы, цифры).
- **Full** (важная внешняя дека / сложный источник): полный цикл критики на каждый слайд + финальный ревью всей деки на полноту (все P0 на месте, все строки реестра использованы, нет провисших слайдов).

### Усилители качества (опционально)
- **Few-shot эталоны:** дай верстальщику 1–2 примера отличных готовых слайдов как образец — слабые модели хорошо имитируют.
- **Голосование на ключевых слайдах:** P0-слайд собери 2–3 раза разными формами, арт-директор выбирает лучший, остальные — на доноров идей.
- **Финальный ревьюер:** отдельный проход «чего не хватает» по всей деке (пропущенная мысль, неиспользованные данные из реестра, провисший слайд).

> Почему это работает на слабой модели: каждый шаг получает маленький, чистый контекст ровно с тем, что нужно; память вынесена в файл и не «протухает»; данные прослеживаемы (реестр с источниками) — выдумать нечего; результат собирается по кусочкам с независимой критикой, а не одним неподъёмным проходом.
